# Adding a database migration

Tally runs on **two databases**: SQLite by default, PostgreSQL when the operator
configures it. Both are first-class. Every schema change has to be made twice, in
four places, and nothing in the type system will tell you if you miss one.

This document is the checklist. Follow it in order.

> **Read this before touching `backend/src/db/`.** The design reasoning behind the
> dual-dialect setup lives in [erd-multi-database-support.md](erd-multi-database-support.md);
> this file is only the procedure.

---

## The one thing to understand first

`db/schema.ts` hands route code a single set of table objects. At runtime those
are the *running dialect's* tables. At compile time they are **always** the
SQLite ones, via a deliberate cast:

```ts
export const games = resolved.games as typeof sqliteSchema.games
```

There is a matching cast on the client itself in `db/index.ts`. The two lies
cancel out, and the arrangement is safe **only while both schemas describe
structurally identical rows**.

So: if you add a column to `schema.sqlite.ts` and forget `schema.pg.ts`, the code
compiles cleanly, every SQLite test passes, and Postgres users get a runtime
error. The compiler is not checking this seam. **The dual-dialect test matrix is
the only thing that is.** Run it.

## Checklist

### 1. Write both SQL migrations

Two files, same number, same name:

```
backend/src/db/migrations/sqlite/00NN_your_change.sql
backend/src/db/migrations/postgres/00NN_your_change.sql
```

Migrations are applied in filename order and recorded in `_migrations`, so a
file that has already run is never re-run. Numbers must not be reused.

**These are twins, not translations.** The net effect must match; the statements
often cannot. `0004_player_type.sql` is the clearest example — SQLite cannot drop
a constraint, so it rebuilds the entire `players` table across seven steps, while
Postgres does it in three `ALTER TABLE`s. Start the Postgres file with a comment
naming its SQLite twin, as the existing ones do.

Dialect differences that have already bitten this project:

| | SQLite | Postgres |
|---|---|---|
| Auto ids | `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY` |
| Add a column | `ALTER TABLE t ADD COLUMN c` | `ALTER TABLE t ADD COLUMN IF NOT EXISTS c` |
| Drop a constraint | not supported — rebuild the table | `ALTER TABLE t DROP CONSTRAINT IF EXISTS ...` |
| Float | `REAL` | `DOUBLE PRECISION` |
| Boolean | `INTEGER` (0/1) | `BOOLEAN` |
| Now, `datetime` format | `datetime('now')` | `to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS')` |
| Now, ISO format | `strftime('%Y-%m-%dT%H:%M:%fZ','now')` | `to_char(now() AT TIME ZONE 'UTC', 'YYYY-MM-DD"T"HH24:MI:SS.MS"Z"')` |
| Foreign keys during a rebuild | `PRAGMA foreign_keys = OFF` **outside** the transaction | not needed |

Prefer `IF NOT EXISTS` / `IF EXISTS` on the Postgres side. Each Postgres
migration runs in its own transaction and is rolled back on failure, so a partial
apply is not a concern, but idempotence makes reruns during development painless.

Timestamps are stored as `text` in both dialects, deliberately. Do not "fix" this
to `timestamptz` — it would change the API contract and the frontend types for no
gain.

### 2. Update both Drizzle schemas

- `backend/src/db/schema.sqlite.ts`
- `backend/src/db/schema.pg.ts`

**Column names must match exactly between the two.** Not the types — those differ
by dialect — the names. `schema.pg.ts` has `NOW_DATETIME` and `NOW_ISO` constants
for the two default expressions; use them rather than writing the `to_char` call
again.

### 3. If you added a table, wire it in four more places

Adding a *column* to an existing table needs none of this. A new **table** does:

| File | What to add | What breaks if you forget |
|---|---|---|
| `db/schema.ts` | An `export const yourTable = resolved.yourTable as typeof sqliteSchema.yourTable` line | Route code cannot import it |
| `db/import-sqlite.ts` → `IMPORT_ORDER` | An entry, **after any table it references** | A SQLite → Postgres migration silently drops the table's rows |
| `db/import-sqlite.ts` → `SEQUENCE_TABLES` | The name, if the table has an auto-generated id | First insert after a migration dies on a duplicate key |
| `test/helpers.ts` → `resetDb()` | The table, in **both** lists — `TABLES` for SQLite and the `names` array for the Postgres `TRUNCATE` | Rows leak between test files and produce confusing failures |

`IMPORT_ORDER` is parent-before-child on purpose. Getting it wrong trips a
foreign key immediately, which is the intended safety net rather than something
to work around.

Whether the table belongs in `state.ts`'s `DOMAIN_TABLES` is a judgement call:
that list decides "does this install have data worth migrating?". Caches and
lookup tables do not belong there. `bgg_games` is deliberately excluded.

### 4. Never write a bare `like()`

SQLite's `LIKE` is case-insensitive for ASCII; Postgres's is case-sensitive. A
bare `like()` silently changes search behaviour for Postgres users — searching
"catan" stops matching "Catan", with no error anywhere.

Use `searchLike()` from `db/search.ts` for all user-facing text search.

### 5. Never call `db.transaction()`

better-sqlite3 requires a **synchronous** callback and rejects one that returns a
promise; node-postgres requires an **async** one. No wrapper can bridge that —
JavaScript cannot synchronously unwrap a promise.

Use `withTransaction()` from `db/transaction.ts`, which is async on both.

### 6. Watch for aggregates

node-postgres returns `int8` (`COUNT`) and `numeric` (`SUM`) as **strings**;
SQLite returns numbers. `db/index.ts` installs type parsers to normalise this, so
existing aggregates are fine — but if you add a column of a numeric type not
already covered there, check what the driver hands back before trusting it.

### 7. Run both dialects

Neither pass alone is sufficient. The SQLite pass will not catch a missing
Postgres migration, and it is the pass that runs by default.

```bash
docker compose -f docker-compose.test.yml up -d --wait
pnpm -C backend test:all
```

`test:all` runs SQLite and then Postgres. CI runs the same matrix on every PR.

### 8. Verify a real migration, not only the suite

Every defect in this project that would have reached a user was found by running
the real thing. Unit fixtures do not carry seeded rows, do not use the WAL, and
do not exercise the build. At minimum, for a schema change that touches the
import path:

1. Boot on SQLite, create data.
2. Restart pointed at an empty Postgres, with the same `DATA_DIR`.
3. Import through the browser and check row counts on both sides.
4. Insert something afterwards — that is what catches a missing `setval`.

## Quick reference

```
backend/src/db/
├── migrations/sqlite/00NN_*.sql     ← 1
├── migrations/postgres/00NN_*.sql   ← 1
├── schema.sqlite.ts                 ← 2
├── schema.pg.ts                     ← 2
├── schema.ts                        ← 3, new tables only
├── import-sqlite.ts                 ← 3, new tables only
├── search.ts                        ← use searchLike(), never like()
└── transaction.ts                   ← use withTransaction(), never db.transaction()
```
